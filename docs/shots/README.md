# Снимки окон Winbox 4 из CI

Эти файлы создаёт workflow `.github/workflows/winbox-shots.yml` — на настоящем
RouterOS, без рисунков и макетов:

1. ставятся QEMU, Xvfb, tesseract, xdotool, ImageMagick, openbox;
2. скачивается CHR RouterOS 7.24.6 и запускается в QEMU (`-cpu max`, диск `if=ide`,
   проброс порта 8291 на 127.0.0.1);
3. поднимается Xvfb 1600×1100, openbox и настоящий Winbox 4.4;
4. `.github/scripts/winbox-nav.py` входит в роутер и открывает окна по списку;
5. всё складывается в артефакт `winbox-shots` и коммитится в ветку
   (`CI: настоящие скриншоты Winbox 4 [skip ci]`).

## Соответствие снимков инструкциям

Снимок попадает **под шаг** только если выполнены оба условия:

1. окно на снимке совпадает с окном шага (`IP → Address`, `WireGuard → Peers` и т.п.);
2. все значимые данные шага (адреса, интерфейсы, имена, лимиты) реально видны на снимке.

«Запасных» кадров того же раздела больше нет. Если кадр пустой или показывает
чужие значения, шаг показывает схему с нужными данными, а не вводит в заблуждение
фотографией. Ручная проверка кадров — `scripts/win4-review.js`, правило привязки —
`scripts/win4-step-rules.js`, отчёт по всем шагам — `docs/shots/step-audit.json`.

На карантин отправлены кадры, где подпись обещала одно, а снято другое:
`wifi-wps` (главное окно WiFi вместо WPS), `bridge-new` (Bridge Filter Rule вместо
New Bridge), `backup` (Cloud Backup с ошибкой CHR free licence вместо Backup).

## Съёмка на настроенном стенде (режим `scene`)

Пустой CHR не может подтвердить инструкцию: в статьях свои адреса, имена и
лимиты. Поэтому режим `scene` сначала **настраивает роутер теми же объектами**,
а уже потом снимает окна:

1. `.github/scripts/ros-api.py` — клиент RouterOS API (порт 8728, проброшен из
   QEMU) без сторонних зависимостей; применяет конфиг построчно и печатает
   отказ по каждой строке. Протокол проверяется самопроверкой
   `python3 .github/scripts/ros-api.py --selftest` ещё до загрузки CHR;
2. `.github/scripts/lab-setup.rsc` — учебный стенд: `bridge-lan`, `wg-office`
   и `10.10.10.5/32`, `192.168.88.1/24`, пулы, PPP-профили, `guest-limit
   20M/20M`, планировщик, Netwatch, правила filter/NAT/mangle. Firewall
   применяется последним, и первое правило разрешает управляющую сеть стенда —
   иначе «drop all from WAN» оборвал бы Winbox и API посреди съёмки;
3. `.github/scripts/scene-list.txt` — окна стенда в порядке важности для
   инструкций; после них обычный проход добирает остальные окна;
4. у QEMU пять сетевых карт: `ether2…ether5` в мосту настоящие, а не выдуманные
   имена;
5. каждый кадр сохраняется в натуральную величину (окно 1560 px, JPEG q90) —
   при увеличении в просмотрщике текст остаётся резким.

### Съёмка частями

Обход 36 окон по OCR не укладывался в 150-минутный лимит job, и прогон
отменялся до публикации — кадры пропадали. Теперь список режется на части:

Один прогон = **все части параллельно**: задание «План съёмки» режет список
и раздаёт части заданиям матрицы. У каждой части свой CHR и свой Winbox,
поэтому лимит одного job больше не ограничивает всю съёмку.

Переснять одну часть вручную (Actions → Winbox 4 → Run workflow):

```
mode=scene   part=2   part_size=10
```

* `part` — пусто: все части матрицей; `N`: только часть N; `0`: весь список
  одним заданием (старое поведение);
* `part_size` — сколько окон в части (по умолчанию 10);
* части — задания одного прогона, они идут параллельно и не отменяют друг
  друга (`fail-fast: false`);
* у каждой части свой отчёт (`report-partN.txt`) и манифест
  (`manifest-partN.txt`), кадры и текст — по именам окон. Файлы частей не
  пересекаются, поэтому параллельные коммиты не конфликтуют при rebase;
* общий `verified.json` в режиме частей не пишется — импортёр читает текст
  прямо из `docs/shots/ocr/<имя>.txt`;
* крайний срок проверяется перед каждым распознаванием: медленное окно не
  съедает бюджет, съёмка останавливается и кадры успевают опубликоваться;
* кадры публикуются сразу после съёмки части (`!cancelled()`), а добор
  остальных окон вынесен в отдельный режим `nav` — раньше он занимал всё
  время отменённого прогона и публикация не выполнялась.

### Как доказывается совпадение

После съёмки кадр читается OCR (`eng+rus`): текст ложится в
`docs/shots/ocr/<имя>.txt` и `docs/shots/verified.json`. Импортёр ставит снимок
под шаг, только если **все значимые значения шага нашлись в тексте кадра**.
Нет совпадения — шаг показывает схему, а не чужую фотографию.

## Как открываются окна

Координаты «пункт дерева y=+105» не масштабируются и не знают про подменю,
поэтому окно ищется по названию:

* `winbox-nav.py` делает снимок экрана, распознаёт текст (tesseract) в области
  дерева или содержимого и щёлкает по найденному месту;
* список того, что снимать, лежит в `.github/scripts/shot-list.txt` —
  `имя|путь в меню|new|путь в приложении`;
* подменю и вкладки проходятся так же: после клика по разделу ищется название
  подпункта (`IP → Firewall → NAT`), для диалогов находится кнопка `New`;
* кадр сохраняется только если окно реально открылось — проверяется разброс
  яркости области содержимого, пустой серый стол не снимается.

## Что важно знать про вход и размер окна

* Порт 8291 у QEMU открывается сразу при старте, поэтому «порт отвечает»
  ничего не значит: RouterOS грузится 8–15 минут. Признак готовности —
  появление дерева меню на экране.
* Основной способ входа — двойной щелчок по строке роутера во вкладке
  **Neighbors** (там CHR виден по MAC `52:54:00:12:34:56`); ввод адреса в
  `Connect to` — резервный.
* В Xvfb нужен оконный менеджер: без openbox Qt не даёт менять размер окна,
  и вкладки Winbox («Interface List», «Registration», «WPS», «PPPoE Client»)
  уезжают за край. С openbox окно растягивается до 1560×1040.
* Перед каждым окном жмём Escape, а каждые 40 окон или после четырёх неудач
  подряд Winbox перезапускается: иначе на экране копятся диалоги и клики по
  дереву перестают доходить.

## Продолжение съёмки

По умолчанию скрипт **добавляет недостающие кадры**: если `docs/shots/jpg/имя.jpg`
уже есть, задача пропускается. Так каждый следующий прогон не переснимает весь
список заново, а добирает то, что ещё не получилось.

* `NAV_RESUME=0` или `FORCE=1` — переснять весь список;
* в workflow_dispatch есть вход `force` для полного пересъёма;
* шаг съёмки больше не замаскирован под `|| true`: трейсбек валит job, а отчёт
  всё равно коммитится шагом с `if: always()`.

## Связь с приложением

```
node scripts/win4-import.js
```

Копирует кадры из `docs/shots/jpg/` в `app/src/main/assets/www/img/shots/`,
собирает галерею `js/data/win4.js` и привязку «шаг статьи → снимок»
`js/data/photos.js`. Подписи к кадрам — `scripts/win4-titles.js`.

Если окно есть в `img/shots`, но статьи про него нет (например, Mesh),
импорт его пропускает: ui-check требует, чтобы каждый файл где-то
использовался, а выдавать одно окно за другое нельзя.
